# ADR-002: Gateway-Owned Provider Payout Data

## Status

Accepted — Revised 2026-07-24

## Date

2026-07-23

## Context

The existing Pagar.me adapter creates order charges and split payments but does not onboard or update recipients. TaskGo stores only a provider recipient identifier, while payout readiness requires a confirmed recipient bank account. Persisting raw financial data locally would expand TaskGo's security and compliance responsibilities and create a second source of truth.

## Decision

Pagar.me will be the authoritative source for provider payout data. TaskGo will extend its gateway boundary to create or update the authenticated provider's recipient and payout configuration.

TaskGo will persist only gateway identifiers, synchronization status, non-sensitive bank completion indicators, and masked metadata required by the user experience. Raw bank-account details will not be returned by profile-completion APIs or used as the local source of truth.

Payment readiness will require successful Pagar.me confirmation of the recipient bank account. Recipient existence alone will not imply readiness. Pix remains a customer payment method and is not a provider payout configuration item.

Pagar.me does not publish a recipient-mutation idempotency contract. TaskGo will therefore own idempotency: scope keys by authenticated provider and operation, reject conflicting reuse, reconcile by persisted recipient identifier and unique external code before creation, and never depend on a gateway idempotency header for correctness.

## Capability Validation — 2026-07-24

Pagar.me Core API v5 publicly documents recipient creation and retrieval, a required default bank account, bank-account replacement, and transfers to that bank account. The public Core v5 recipient and transfer references do not document a payout Pix-key resource or mutation.

TaskGo approved the gateway-confirmed bank account as the sole payout requirement on 2026-07-24. Customer Pix charges remain unchanged and must not be interpreted as provider payout-key support. No provider Pix key will be collected or stored in this feature.

See [Pagar.me Core v5 Payout Capability Report](../pagarme-capability-report.md).

## Alternatives Considered

### Alternative 1: Store Financial Data Locally

- **Description**: Persist bank-account values in TaskGo and synchronize them with Pagar.me.
- **Pros**: Gives TaskGo direct control over all form and synchronization states.
- **Cons**: Duplicates sensitive data, increases compliance exposure, and creates conflicting sources of truth.
- **Why rejected**: TaskGo does not need raw financial data after the gateway accepts it.

### Alternative 2: Store a Provider Pix Key for a Future Payout Rail

- **Description**: Keep a provider Pix key in TaskGo even though Pagar.me does not use it for recipient settlement.
- **Pros**: Preserves the option to add a separate Pix payout rail later.
- **Cons**: Collects sensitive information that has no function in the approved payout flow and creates misleading readiness semantics.
- **Why rejected**: YAGNI and data minimization require omitting data that the current payout provider cannot use.

### Alternative 3: Gateway-Hosted Onboarding

- **Description**: Redirect providers to an onboarding interface hosted by Pagar.me.
- **Pros**: Minimizes TaskGo's handling of financial input and delegates more validation to the gateway.
- **Cons**: Depends on an unconfirmed product capability and reduces control over the centralized completion journey.
- **Why rejected**: The current integration exposes no hosted onboarding flow, and the approved experience requires TaskGo-controlled progress and navigation.

## Consequences

### Positive

- Reduces local handling and exposure of sensitive payout data.
- Keeps gateway acceptance as the authoritative readiness signal.
- Supports masked confirmation without exposing financial values to the provider home.

### Negative

- The completion flow depends on Pagar.me availability and recipient capabilities.
- TaskGo must map gateway states and errors into stable internal statuses.
- Existing providers require reconciliation against current gateway recipients.

### Risks

- Retried requests may create duplicate gateway resources; enforce TaskGo-owned idempotency and reconcile by persisted identifiers and unique external recipient code.
- Gateway and local status may diverge; refresh status after mutations and support controlled reconciliation.

## Implementation Notes

Add recipient-onboarding methods behind the existing Pagar.me service boundary. Authenticated provider endpoints must derive the provider identity from the access token. Logs and API responses must exclude raw bank and document values.
