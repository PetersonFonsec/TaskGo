# ADR-003: Server-Derived Profile Completion Resource

## Status

Accepted

## Date

2026-07-23

## Context

The provider home currently reads an aggregate cached in the login session. That state cannot refresh reliably after profile edits, and the existing frontend session update method does not update its signal. Completion also spans multiple domains: payout configuration, user photo, provider social links, and user addresses.

The system needs one consistent readiness calculation without coupling every mutation to the login response or duplicating completion rules in Angular.

## Decision

TaskGo will expose an authenticated provider profile-completion resource calculated by the backend from authoritative domain state. A dedicated query endpoint will return the four checklist statuses, grouped progress, payout readiness, and overall completion. It will not return frontend route URLs or sensitive values.

Each domain will retain a focused mutation:

- Payout mutations will update the gateway-owned recipient bank-account configuration.
- Photo upload will use a TaskGo-managed multipart endpoint, validate the image, store it through the configured file-storage boundary, and persist only its URL.
- Social links will use structured WhatsApp, Instagram, Facebook, and LinkedIn fields with per-field validation and one update operation.
- Address mutations will reuse the address domain after enforcing ownership through authenticated identity.

The Angular completion service will own the query state. Successful domain mutations will invalidate and refetch it so both the home CTA and centralized page render current server-derived status.

## Alternatives Considered

### Alternative 1: Extend the Login Aggregate

- **Description**: Add completion status to the existing provider-home payload returned during login.
- **Pros**: Avoids an additional request on initial home load.
- **Cons**: Produces stale status, couples profile readiness to authentication, and still requires a refresh mechanism.
- **Why rejected**: Completion changes during the session and must refresh independently.

### Alternative 2: Single Read-and-Write Completion Endpoint

- **Description**: Query and mutate all checklist domains through one profile-completion API.
- **Pros**: Gives the frontend one entry point for every action.
- **Cons**: Mixes unrelated validation, ownership, file upload, financial integration, and address behavior.
- **Why rejected**: Focused mutations preserve existing domain boundaries while one query provides consistent status.

## Consequences

### Positive

- Completion rules have one server-side source of truth.
- Home and centralized page share a refreshable frontend state.
- Domain-specific validation and authorization remain isolated.
- Existing data contributes to completion without re-entry.

### Negative

- The provider home performs one additional authenticated query.
- Several incomplete existing flows must be secured or completed before they can participate.
- Structured social fields require schema evolution when the supported network list changes.

### Risks

- Completion state may briefly lag after external gateway updates; refetch after mutations and define a pending synchronization status.
- File storage configuration may differ by environment; require a storage adapter and stable public URL behavior.
- Existing address endpoints allow unsafe ownership assumptions; do not expose address completion until authenticated filtering and mutation ownership are enforced.

## Implementation Notes

Place shared request and response contracts in the existing shared library. Keep frontend destinations as an Angular mapping from checklist item identifiers. Use provider-scoped routes and token-derived user/provider identifiers.
